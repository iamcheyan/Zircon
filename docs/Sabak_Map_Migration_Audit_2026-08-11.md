# 沙巴克 3 号地图专用图库移植审计

日期：2026-08-11

## 结论

当前沙巴克地图缺墙、屋顶断裂和竖向贴图缺块，主要原因不是 `Sabak.Zl` 部署失败，也不是 Godot 的地图坐标布局，而是移植工具改写中层/前景贴图索引时发生了 `-1/+1` 双重偏移。

原版客户端读取 `.map` 的逻辑是：

```text
读取地图原始索引 raw
保存为 raw + 1
绘制时使用 (raw + 1) - 1
```

因此运行时实际使用的图库帧就是 `.map` 文件里的原始索引。移植工具却把中层和前景索引当成已经加 1 的值处理：

```python
real_mi = mi - 1
new_img = frame_map[(file, real_mi)]
写回 new_img + 1
```

这会导致：

1. 提取图库时提取了前一帧；
2. 改写地图时又把新帧号加了一次；
3. 游戏运行时实际取到合并图库的后一帧；
4. 后一帧如果是空帧，就表现为整齐的墙体/屋顶缺口；
5. 其他情况下表现为墙体错位、碎片化或使用相邻建筑贴图。

## 证据

错误位置：

- `移植工具/merge_map_libraries.py` 的 `collect_refs()`：中层和前景使用 `mi - 1` / `fi - 1`；
- `移植工具/merge_map_libraries.py` 的 `rewrite_map()`：写回时使用 `new_img + 1`；
- `移植工具/build_sabak_package.py` 中存在完全相同的逻辑。

以原始沙巴克地图的中层引用为例，地图原始值为 `4026`，工具却按 `4025` 提取，并将新索引再次加 1 写回。验证工具也使用了同样的错误约定，所以之前的“没有越界”结论不能证明地图引用正确。

当前部署文件与移植包本身一致：

- `3.map`：部署文件与移植包哈希一致；
- `Data/Map Data/Sabak.Zl`：部署文件与移植包哈希一致。

这说明问题发生在生成过程，而不是复制部署过程。

## 正确的转换规则

对中层/前景的普通引用：

```python
raw_img = 地图中的原始值
new_img = frame_map[(file_id, raw_img)]
地图中写回 new_img
```

对背景层，原有的直接索引转换方式保持不变。

哨兵值必须在减法之前判断：`raw_img >= 65000` 时保留哨兵值，不能先执行 `raw_img - 1`。

## 重新生成注意事项

必须使用未改写的 Zircon 原始 `3.map` 作为输入重新生成。不能使用已经改写成 `file=200` 的当前地图再次运行移植工具，否则会把专用图库编号当成原始图库编号处理。

重新生成后需要验证：

1. 中层/前景每个地图引用都能在原始图库中找到对应帧；
2. 新地图实际写入的索引等于 `frame_map[(原 file, 原 raw index)]`；
3. 所有非哨兵引用都能在 `Sabak.Zl` 中解码；
4. 重新部署客户端和服务器两份 `3.map`，并重启客户端/服务器。

## 小地图绑定（独立于地图几何）

本次检查还发现 `3.map` 的地图资源与小地图绑定曾被混用：`3.map` 使用 Zircon
原版，但 EI 小地图迁移把数据库中的 `MapInfo(FileName=3).MiniMap` 改成了
18（EI `FMMap` 第 17 帧）。旧 Zircon 数据的正确绑定是第 7 帧。

已修正为：

- `Debug/Client/Data/MiniMap.Zl`：保留 EI 287 帧，仅将 frame 7 替换为 Zircon
  原版 Sabuk Keep 小地图，尺寸 `800×600`，offset `(0,0)`；
- `Debug/Client/Data/System.db`：`3 -> 7`；
- `Debug/ServerCore/Database/System.db`：`3 -> 7`；
- EI frame 18 仍保留为 `300×200`，其它 EI 地图绑定不变。

验证不能只看数据库数字：用 Godot 实际 `ZlReader` 读取混合图库，确认 frame 7 与
frame 18 的尺寸和定位；数据库 report 再独立确认客户端/服务器两份值均为 7。
