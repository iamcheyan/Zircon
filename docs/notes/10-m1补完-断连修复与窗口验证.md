# 讨论记录 10：M1 补完——StartGame 断连修复与"窗口模式验证"方法论

> 日期：2026-08-06
> 关联：讨论 05 走通登录/选角色，但进游戏时闪断；本篇记录闪断根因与修复，以及一个重要的验证教训——**"看不见"不等于"没渲染"，很可能是你根本没在看对的画面**。
> 结论：进游戏断连的根因是"回包里带的物品数据在客户端还没加载物品数据库时就被处理"（空引用崩溃），改 3 处后稳定；窗口模式验证引入了"程序内自动截图"，一举揭开了一个持续多轮的"地图只画一条竖带"假象——那是旧截图文件造成的误判，真实的地图渲染一直正常。

---

## 1. 症状：一切正常，唯独进游戏就断线

前面几轮我们已经能做到：启动客户端 → 自动登录 → 选角色 → 点"进入游戏"。服务端也返回了 `StartGame` 成功。可就在这之后，客户端立刻断线，退回登录。

断线的直接原因（日志里能看到）：**客户端处理回包时抛了空引用异常（NullReferenceException）**。一次异常被我们自己的异常处理器吞掉、只打日志，但网络模块已经认为连接坏了，于是断开。

## 2. 根因：一条"物品数据"牵出了顺序问题

服务端在 `StartGame` 回包里，附带了角色背包里的一件件物品（`ClientUserItem`，即"客户端看到的物品条目"）。客户端收到后要调用它的 `Complete()` 方法，把它和物品数据库里的定义"配对"。

问题就出在：**配对时要查 `Globals.ItemInfoList`（物品信息表），而这个表在进游戏的那个瞬间还没加载**。查一个空表 → 空引用 → 崩溃 → 断线。

一句话：**服务端数据到了，客户端的"字典"还没准备好**。这不是网络问题，是客户端内部的初始化顺序问题。

## 3. 修复：三处小改动

1. **把进游戏信息（StartInfo）从选角色场景传给游戏场景**，游戏场景在创建时就知道玩家是谁，不用等回包。
2. **StartGame 成功回包在主线程直接处理**（之前通过延迟调用，时机更乱）。
3. **查地图文件时用安全写法**：`Globals.MapInfoList?.Binding.FirstOrDefault(...)`，表没加载就得到空而不是崩溃。

验证：headless 连续跑三次，`Process 异常 = 0`、无 `Disconnect`，角色正常进入游戏、显示坐标和地图。

## 4. 大教训：验证"画面"不能用"猜"

M1 结论里写着"地图渲染走通"——但那是 **headless（无头）模式**下跑的，Godot 在无头模式根本不执行画面绘制，当时只是"代码能跑不报错"。真正的画面效果从未亲眼确认。

这一轮开始做**窗口模式验证**，暴露了整套验证链条的脆弱性：

- 游戏窗口要显示在 X 窗口系统上，靠 `xdotool` 模拟按键 F12 触发截图。
- **但无窗口管理器时，`xdotool windowactivate` 常常不生效**——按键根本没送到新窗口！
- 结果：截图像素分析一直在读**上一轮的旧截图文件**。于是得出"地图只渲染一条竖带"、"红色测试矩形不显示"等一连串错误结论，白折腾了数轮。

**正确做法：让程序自己截图。** 在游戏场景里加了一个定时器：进游戏 5 秒后，程序内部直接调用 `GetViewport().GetTexture().GetImage()` 存盘——完全绕开键盘焦点问题。文件里还打印了截图尺寸作为"这次是新文件"的凭证。

教训总结：**调试渲染问题，验证手段本身必须先可靠**。截图文件的时间戳、尺寸日志，都是防呆凭证。

## 5. 顺带挖出的真 Bug：地图解析偏移 2 字节

在做地图数据统计时发现：所有格子的"中层文件号"都是 255（无效值）。对照原客户端源码，发现它读地图文件时先 `Seek(22)` 读宽高，再 **`Seek(28)` 才读数据**——我们的读取器读完了宽高就停在偏移 26 直接读数据，**整体错位 2 字节**，所以解析出来的全是垃圾。

修复一行：读完宽高后 `Seek(28, SeekOrigin.Begin)` 再开始读。修完后：背景文件号 0（对应地面图库 Tilesc）、背景贴图号 7064 等全部正常。

这解释了"地图为什么空"的最后一个疑点——而且它本来就不存在（见上节，那是旧截图误判）。
