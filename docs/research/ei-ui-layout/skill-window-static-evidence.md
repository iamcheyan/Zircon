# EI 3.0 技能窗口：静态证据记录

更新时间：2026-08-09

## 结论先行

原版 `Mir3.exe` 的主界面初始化在 `0x00427904` 构造一个使用
`Data/GameInter.wil` Frame 400 的窗口。Frame 400 是 296×332 的打开书本外框；
同一个窗口包装器 `0x00439250` 又创建了 11 个成对控件（普通帧/按下或悬停帧）。
其中 8 个控件的构造调用前紧邻明确的 GB18030 中文字面量，因此它们不是单纯
“根据截图猜的按钮”，而是原版代码中确实存在的分类文字控件：

| 原文字 | 分类候选 | 普通/状态帧 | 构造调用 | 目前可确认的相对位置 |
|---|---|---:|---:|---:|
| 火 | fire | 450/451 | `0x00439334` | (5,21) |
| 冰 | ice | 452/453 | `0x0043935D` | (3,56) |
| 电 | lightning | 454/455 | `0x00439386` | (4,91) |
| 风 | wind | 456/457 | `0x004393B3` | (2,126) |
| 神圣 | holy | 458/459 | `0x004393E0` | y=161，x 仍需解析 |
| 黑暗 | dark | 450/451 | `0x0043940D` | x=196，y 仍需解析 |
| 幻影 | illusion | 452/453 | `0x00439437` | x=231，y 仍需解析 |
| 剑 | sword | 454/455 | `0x00439464` | 仍需解析 |

这些坐标是窗口内部坐标，不是最终屏幕坐标。窗口初始屏幕原点还必须结合
窗口基类初始化参数和运行时移动逻辑确认；不能把当前 Zircon 的窗口位置反推为
原版位置。

## 关键调用链

```text
0x00427904  主 UI 初始化
    └─ 0x00439250  技能窗口包装器
         ├─ 0x00423B30  窗口/基类初始化候选
         ├─ 0x00417550  11 次通用控件构造
         └─ 0x00439150  窗口自身初始化候选
```

通用控件构造器 `0x00417550` 的字段意义已经通过其实现确认：

| 对象偏移 | 含义 |
|---:|---|
| `+0x04` | 命中矩形 RECT |
| `+0x14` | 贴图库/资源句柄 |
| `+0x18` | 普通帧 |
| `+0x1C` | 状态帧 |
| `+0x28` | X |
| `+0x2C` | Y |
| `+0x30` | 回调/附加字段候选 |
| `+0x34` | 控件文字缓存候选 |

因此，后续实现预览器时应直接按 `frame_pair + (x,y) + hit_rect` 生成调试层，
不要先手动拖动再把拖动值当作证据。

## `Magic.exp` 与 `magic.dat` 的边界

代码中的字面量是裸名 `Magic.exp`，供应的 EI 客户端文件为：

```text
/home/tetsuya/NAS/TMP/EI传奇3.0客户端/Magic.exp
```

不是 `Data/Magic.exp`。该文件当前表现为编码/加密二进制，不能因为窗口代码引用
它就直接声称已经得到完整技能名称、等级或页签内容。

另有一套独立文件：

```text
/home/tetsuya/NAS/TMP/Mud3/Envir/magic.dat
```

它属于 Mud3 服务端数据，现有 `docs/research/mud3-dat-decoded/` 已对其 105 条
记录做了解码与 Zircon 对照。这些数值可以作为内容百科的老版技能资料，但不能
替代 EI 客户端 `Magic.exp` 的 UI 读取证据。两套数据要在最终网站中分别标注来源。

## 已确认的 `Magic.exp` 初始化/加载链

在技能窗口自身初始化函数 `0x00439150` 中可以看到一条比“字符串引用”更强的
静态证据链：

```text
0x00439150
  ├─ 准备 16 字节栈上初始化/密钥候选
  ├─ 0x00452580：把该初始化数据交给外层对象/解码上下文候选
  ├─ 0x0046926D("Magic.exp", "/%s")
  ├─ 返回数据对象
  ├─ 读取返回对象 +0x10
  ├─ 0x00469382 / 0x00468B1A：取得数据流/缓冲句柄候选
  └─ 保存结果到窗口对象 this+0x968
```

其中 `0x0047C2FC` 的字面量确实是 `Magic.exp`，`0x0047BCF8` 的字面量是
`/%s`，二者被同一加载包装函数使用；析构函数 `0x00439220` 会释放并清零
`this+0x968`。这说明它是窗口持有的运行时资源或数据流句柄，而不是仅用于显示
的常量。

目前仍不能从这条链单独证明 16 字节数据的密码算法、记录长度、技能名称字段、
等级字段或页签映射。故 `Magic.exp` 的“被加载”证据等级为
`primary-static-loader-chain`，字段语义仍为 `pending-runtime-or-deeper-static-analysis`。

## 下一步证据路线

1. 从 `0x00439150`、`0x00439220` 及窗口析构/输入分支追踪技能页签点击后的字段。
2. 继续反汇编 `0x00452580`、`0x0046926D`、`0x0046921B`、`0x00469E94`、
   `0x0046D450`、`0x0046D4DD`，恢复初始化数据、文件缓冲和记录长度的真实语义。
3. 对 `0x004393E0` 之后几个使用栈上参数的控件，恢复包装器参数的真实语义，补齐
   神圣/黑暗/幻影/剑四个控件的 X/Y 和 RECT。
4. 读取 `Magic.wil`、`MIcon.wil` 与 `GameInter.wil` 的帧联系，确认书页中的技能
   图标、选中态、锁定态和等级数字是否由代码绘制或由贴图提供。
5. 在 800×600 预览器中加入“原始静态证据 / 运行时确认 / 视觉候选”三级标签，
   任何未确认的坐标都显示为候选而不是伪装成最终值。
